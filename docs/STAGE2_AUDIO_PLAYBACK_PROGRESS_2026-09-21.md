# 阶段 2：背景音乐进度状态收敛

> 日期：2026-09-21
>
> 范围：P2-A13
>
> 结论：背景音乐的开始、暂停、恢复、停止和进度估算已从音频页面提取为专用控制器；进度同步同时绑定后端媒体 ID 与播放会话，并跟随多终端共享的暂停状态。

## 1. 根因与修正

旧 `AudioPage` 直接维护 interval、曲目总时长、累计播放时间和当前计时段起点。页面只监听 `currentMediaId`，存在三个边界问题：

1. 单曲循环或同曲重播时，媒体 ID 不变，但后端会创建新的 `playbackSession`；旧进度不会归零，可能停在 100%。
2. VBR 音频时长探测最长等待 6 秒；同一媒体在等待期间进入新会话时，只比较媒体 ID 无法识别旧异步结果。
3. 暂停和继续只由当前页面按钮直接控制计时器；另一台手机或管理终端改变后台暂停状态后，本页进度仍继续走或保持停止。

本批新增 `frontend/src/features/playback-progress-controller.ts`，集中管理纯本地的视觉进度估算。页面以后台 `currentMediaId + playbackSession` 作为播放实例身份；新会话立即停止旧估算，时长探测完成前再次校验媒体与会话；`paused` 变化直接驱动控制器暂停或恢复。

后台播放通道仍是唯一权威来源。控制器不决定当前曲目、不自动切歌、不调用播放 API，也不持久化状态。

## 2. 行为不变量

- 播放、暂停、继续、停止、上一首和下一首仍调用原有 playback store 与 API。
- 曲目推进、循环和随机策略仍由后端及 GK9000 背景音乐守护执行。
- 已知时长按 300ms 更新视觉进度；未知或非法时长保持 0，不创建空转计时器。
- 暂停只累计真实运行时间，暂停期间经过的墙钟时间不计入进度。
- 已暂停的新播放会话保留时长，后台恢复后可继续计时。
- 到达 100% 后停止计时，不能被普通 resume 重启；新的后台播放会话才能归零重启。
- 页面离开或卸载时清理计时器，keep-alive 返回后重新从后台通道收敛。

## 3. 数据与发布边界

- 无数据库迁移，不读写生产配置、媒体或播放列表，不操作音频设备。
- 自动测试使用注入时钟和调度器，不访问网络、不发送现场播放命令。
- 发布分类为 `frontendCode=true`、`backendCode=false`、`highRisk=false`、`scope=frontend`。
- 生产执行前端旁路构建和原子切换，明确跳过数据库备份、后端构建与服务重启。
- 数据库迁移门禁返回 `MIGRATIONS_CURRENT`，上一代 45 个 PWA 资源继续保留。

## 4. 自动验证

本批新增 5 项回归：

1. 进度按注入时钟计算并在总时长处停止；
2. 暂停和恢复只累计活跃播放时间；
3. 初始暂停的播放实例保留时长并可恢复；
4. 未知时长不启动计时，reset 清理活动实例；
5. 页面必须消费专用控制器、监听后台暂停状态并以播放会话防止旧结果提交。

## 6. 后续边界

音频页仍包含播放列表用例、媒体时长探测、场景长按、静音渐变和配置编辑。下一批应优先提取不直接操作设备的播放列表/时长探测编排，或先转向其他超大页面的纯模型边界；静音渐变同时涉及并发计时和真实音量命令，应在明确取消、失败和设备确认语义后单独处理。
