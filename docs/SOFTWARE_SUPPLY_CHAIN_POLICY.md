# 软件供应链与依赖更新策略

## 1. 唯一版本来源

- 后端和前端分别以 `package.json` 声明兼容范围，以 `pnpm-lock.yaml` 锁定实际版本。
- 本地、CI 和生产统一使用 `pnpm@10.33.4`，安装必须带 `--frozen-lockfile`。
- 禁止提交 npm、Yarn 或其他重复锁文件，也禁止部署脚本在缺少 pnpm 时退回其他包管理器。

## 2. 软件物料清单

`.github/workflows/software-supply-chain.yml` 为后端和前端分别生成 SPDX JSON 软件物料清单（SBOM）：

- 依赖锁文件变化、每周定时任务或人工触发时生成；
- 只安装生产依赖，安装阶段禁用依赖脚本；清单只扫描实际安装包，明确排除锁文件中的开发依赖和依赖包自带的工作流样例；
- 生成器 action 固定到不可变提交，Syft 版本单独固定；
- 对包数量、版本信息和关键生产包做完整性检查，空清单或缺失关键包直接失败；
- SPDX 文档命名空间、来源链接和产物名都包含真实源码提交号；清单通过完整性与来源校验后才上传并保留 90 天，可从对应 GitHub Actions 任务下载。

SBOM 是依赖盘点和漏洞定位证据，不替代锁文件、生产依赖审计或构建测试。

## 3. 定期更新

Dependabot 每周二按以下顺序检查：

1. 10:00 后端 npm 生态；
2. 10:15 前端 npm 生态；
3. 10:30 GitHub Actions。

后端和前端只自动提出 minor/patch 更新，主版本升级必须按独立兼容批次人工规划。更新只创建 PR，不自动合并；每个 PR 仍须通过生产依赖审计、全量测试和构建。GitHub Actions 更新同样只创建 PR，并由相关工作流实际运行后再合并。

## 4. 处置规则

- critical/high 公告：CI 和生产发布立即阻断，建立独立修复批次。
- moderate 公告：记录可达路径、临时控制、责任批次和截止时间，不允许无期限豁免。
- low 或无公告更新：进入每周受控 PR，禁止绕过测试批量合并。
- 依赖主版本、数据库驱动、框架、构建器和原生模块：必须单独交付，并执行空库迁移和真实启动验证。
