## 一、部署与进程管理

### 1. 双看门狗抢端口：前端崩溃循环 421 次，死了一整天（2026-07-15）
- **症状**：PWA 打不开；pm2 里前端进程反复 EADDRINUSE 崩溃重启；而部署脚本每次都报"更新完成"。
- **根因**：老的计划任务 `while(true){ node ... }` 循环和 pm2 同时守护同一个服务，两个看门狗抢 3200/5173 端口，输家崩溃循环；部署脚本只探后端 health，前端死活不看。
- **根治**：pm2 成为**唯一进程属主**（2026-07-16 起），旧循环脚本废除；新增 `scripts/verify-deploy.js` 作为"跑绿"唯一判据（5 条：pm2 online / 端口持有者 PID==pm2 PID / 进程启动时间>产物 mtime / HTTP 实测 / 重启计数 3s 稳定）。
- **防回退**：任何新的"自动拉起"机制都不准绕过 pm2 直接起 node。

### 2. "部署成功"但跑的是旧代码：孤儿进程霸占端口（2026-07-16）
- **症状**：构建成功、health 200，但业主看到的还是旧版本。
- **根因**：pm2 守护死过一次后，它曾管的 node 进程作为孤儿活着继续霸占端口；pm2 新起的进程 EADDRINUSE 崩溃，健康检查打到孤儿身上照样 200。
- **根治**：verify-deploy.js 的 B 判据（端口持有者==pm2 PID）+ 恢复流程先清端口再 resurrect。

### 3. GBK 吞换行：.ps1 脚本静默少执行一行（2026-07-16，多次复发）
- **症状**：脚本某个赋值/一行代码"消失"，报 `Test-Path: Path is null` 之类的莫名错误。
- **根因**：PowerShell 5.1 在中文 Windows 按 GBK 读**无 BOM** 的 UTF-8 .ps1，中文注释的字节序列会把紧随的换行吞掉，下一行代码被并进注释。
- **规约**：`deploy-from-ci.ps1` / `start-players.ps1` / `player-watchdog.ps1` 等保持 **ASCII-only 注释**；其余 .ps1 必须存成 **UTF-8 带 BOM**。新建 .ps1 先确认 BOM。

### 4. 无人值守重启后服务 11 小时没拉起（2026-07-17）
- **症状**：GK9000 凌晨 01:07 无人登录时重启，3200/5173 一直不起，5 分钟兜底任务拒绝执行。
- **根因**：`SmartControlBackend` 计划任务是 Interactive 登录类型——"仅该用户已登录时运行"，没人登录就全部拒跑。
- **根治**：改 **S4U**（"无论用户是否登录"），触发器 AtStartup + AtLogon + 5 分钟重复兜底（见 `scripts/setup-boot-task.ps1`）。注意 PlayerWatchdog 例外：kiosk 窗口必须要控制台会话，保持 Interactive。

### 5. 隧道时通时断、部署随机超时（2026-07-19/20）
- **症状**：GK9000 自己上网正常（git fetch、心跳都通），但跳板机主动连它经常超时，部署失败。
- **根因**：GK9000 在 NAT 后，空闲几分钟 NAT 映射过期，外面就再也**主动**连不进来——单向不对称，所以看起来"时好时坏"。
- **根治**：WireGuard `persistent-keepalive 25`。`wg set` 是运行时配置、重启即失，所以 `boot-pm2.ps1` 每次运行（开机+每 5 分钟）幂等重放。

### 6. 整机卡死，物理断电才救回（2026-07-25）
- **症状**：现场卡到连 shutdown 命令都 spawn 不出来。
- **根因**：几十个孤儿 pm2 守护堆积耗尽进程创建资源。孵化源之一：非交互会话里 `$env:APPDATA`/`USERPROFILE` 为空，拼出来的 PM2_HOME 各不相同，每个 pm2 调用都找不到守护就新孵一个。
- **根治**：PM2_HOME 固定 `C:\Users\user\.pm2`（机器级环境变量 + 各脚本显式 set + WMI 命令行注入）；watcher 心跳里**禁调 `pm2 jlist`**；后来又加了守护去重兜底（见第 9 条）。

### 7. "CI 绿了生产死了"：SSH 会话陷阱（2026-07-25/26）
- **症状**：部署全绿，几小时后（或 SSH 一断开）前后台同时死，期间没有任何新提交。
- **根因**：Windows OpenSSH 会话退出时杀掉整棵进程树。在 SSH 会话里顺手 `pm2 resurrect`/`pm2 start`，守护就绑在会话上——会话一断守护带着两个服务一起死。
- **根治**：所有恢复路径的 pm2 拉起一律走 **WMI Win32_Process.Create 脱离**（`boot-pm2.ps1`、`deploy-from-ci.ps1` 的 `Invoke-DetachedResurrect`），并在命令行里注入 PM2_HOME（WMI 不传调用者环境）。
- **防回退**：永远不要在 SSH/计划任务会话里直接 resurrect/start pm2 守护。

### 8. 生产全挂 + 恢复点被毁：空 dump.pm2（2026-07-26）
- **症状**：前后台全死；`pm2 resurrect` 无效——dump.pm2 是空的。
- **根因**：守护已死时执行 `pm2 save`，pm2 新孵一个**空**守护并用空进程表覆盖 dump.pm2，把唯一恢复点毁掉。
- **根治**：三段自愈链（`pm2 kill` → 清 3200/5173 端口占用 → WMI 脱离 `resurrect & start ecosystem & save` 一条命令内完成）；恢复分支里**禁止 in-session `pm2 save`**。

### 9. pm2 僵尸守护堆到 146 个（2026-07-27，附完整证据链）
- **症状**：体检发现 node 进程 130+，全是 `pm2\lib\Daemon.js` 空转僵尸；服务本身一直正常，CI 一直绿，僵尸静默累积。
- **排查过程**（三轮探针取证，值得学习）：先用命令行去重定性（×146 全是 Daemon.js）→ 采创建时间/会话/父进程（都在部署时间窗）→ 管道清单排除 PM2_HOME 假设（这版 pm2 在 Windows 用**固定管道名** `\\.\pipe\rpc.sock`，与 PM2_HOME 无关）→ boot-pm2.log 逐轮记录洗清 5 分钟兜底任务嫌疑 → `pm2 ping` 对照实验（健康态净增=0）锁定**部署窗口竞态**。
- **根因**：部署/更新时 CI 和盒上 watcher 的多个 pm2 命令并发，探活 ping 超时的客户端孵新守护；新守护抢不到固定管道成僵尸；客户端随后连上老守护把活干成——所以功能全对、僵尸只增不减。次要诱因：`cmd /c "set PM2_HOME=... && pm2"` 的 `&&` 前空格会被 cmd 算进变量值（尾随空格）。
- **根治**：① 所有 `set PM2_HOME=...&&` 紧贴值；② `boot-pm2.ps1` 每 5 分钟**守护去重**——只回收"无 node 子进程 + 不在 pm2.pid + 存活满 10 分钟"的空转僵尸（正常守护三重保护，绝不误杀）。实测 146→2 稳态。
- **防回退**：守护健康态基线 = Daemon.js ×1~2 + backend fork ×1 + vite fork ×1；探针体检段每轮输出，超标会 WARN。

### 10. 隧道部署误报红：生产明明健康（#214/#227 型，2026-07-27）
- **症状**：Actions 报 `GK9000 is at X, expected Y` 红掉，上机检查一切正常。
- **根因**：盒上 `auto-update-watcher`（每分钟）常抢在 CI 之前把 GK9000 拉到目标提交甚至更新的提交；CI 校验步骤做**严格相等**比对就误报。
- **根治**：`deploy-from-ci.ps1` 两道容忍——deploy 分支"already deployed or superseded"短路；VerifyOnly 分支按**祖先关系**放行（请求的提交已包含在当前 HEAD 即绿）。落后/分叉仍然报红。勿回退成严格比对。

### 11. 生产机前端构建 OOM（2026-07-25）
- **症状**：GK9000 上 `pnpm build` 报 "Zone Allocation failed"，dist 残缺，全靠 PWA 缓存硬撑。
- **根因**：pdfjs-dist 引入后 vue-tsc 类型检查在 16G 内存的 GK9000 上 OOM。
- **规约**：生产机只跑 **`build:deploy`**（纯 vite build）；类型检查放本地和 CI。

## 二、播控与现场

### 12. 大屏显示 Windows 桌面，但一切监控指标正常（2026-07-26）
- **症状**：LED 墙显示桌面；后台看 kiosk 心跳全活。
- **根因**：LED 屏断电重启后显示器拓扑变化，kiosk 窗口漂移/丢失；watchdog 只看进程存活，看不出"窗口不在该在的屏上"。
- **处置机制**：改 `scripts/relaunch-players.token` 内容（任意新字符串）→ 推 main → watchdog 下一分钟强制重启所有 kiosk 窗口（`logs/player-relaunch.done` 记录已执行）。前端界面/待机页更新后 kiosk 不会自己刷新，也用这个机制。
- **另**：有人挂 RDP 会抢走控制台会话，watchdog 主动退让并在 RDP 断开后 tscon 抢回。

### 13. 现场屏幕弹窗、任务栏闪现（2026-07-26）
- **症状**：大屏时不时弹出 PowerShell 窗口、任务栏闪现。
- **根因**：`SmartControl-AutoUpdate` 计划任务直接启动 powershell.exe（交互会话里会闪窗）。
- **根治**：任务动作改 `wscript.exe run-hidden.vbs` 静默启动；watchdog 里带一次性迁移，新机器跑一遍自动修。

### 14. PWA 连不上 / 界面是旧的（常发）
- **症状**：平板 PWA 打不开或界面停在旧版，后台实际正常。
- **根因**：Service Worker 缓存了旧前端（含旧的 API 地址/逻辑）。
- **处置**：完全杀掉 App 再重开；不行就系统设置里清该 App 数据。欢迎页等大文件已从 precache 排除（`vite.config.ts` 的 `globIgnores`），别再把大资源塞进 precache。

### 15. 平板心跳失联 "request entity too large"（历史）
- **根因**：监控心跳 payload 无封顶，塞大对象后被后端拒收。
- **根治**：payload 封顶；**别在心跳里塞大对象**。

## 三、设备接入

### 16. 电源时序器"开了又弹回"（2026-07 中旬）
- **根因**：Modbus 状态解析的通道段偏移方向修反（正确是**左移 1 字节**）。
- **防回退**：动 `parseStatus` 前先看提交 `114c6e4` / `714243f`。

### 17. 投影仪电源开关不生效（2026-07-26）
- **症状**：投影仪卡片的电源开关关不掉投影。
- **根因**：电源回路数据绑错——投影仪曾绑在时序器第 8 路（实际是分区喇叭电源）；实际接线：**投影仪=第 5 路，视频融合器=第 4 路**，两台同开同关。
- **根治**：`power-circuits.service.ts` 启动自愈把 `seq-4`/`seq-5` 的 code↔relayChannel 恢复正确（幂等）；ProjectorPage 一个开关串行控制 `seq-5,seq-4` 两路。改路号映射一律走这种幂等自愈，别手改数据库。

### 18. 灯光路由：组号会重复（2026-07-16 重构，接手必读）
- **根因**：两台 CY-DALI64A 共用一条 RS485（USR 透传，slaveId 1/2），**daliGroup 组号跨网关重复**。
- **规约**：灯组唯一键是 `(gatewayCode, daliGroup)` 二元组，路由必须带 slaveId；分区下发串行扇出（RS485 并发帧互踩）。

### 19. 音频矩阵接线基线（2026-07-26 现场核定，勿改）
- EKX-808 @ `192.168.50.61:9761`。输入：IN1/2=LED 屏左右声道、IN3/4=投影仪左右、IN5=USB 声卡、IN6=调音台、IN7=定时播放器、IN8=空。输出：OUT1/2=LED 屏、OUT3/4=投影仪、OUT5=二楼办公区、OUT6=二楼走廊区、OUT7=前厅和东北区、OUT8=一楼展位。
- 默认路由/命名在 `audio-config.service.ts`（含一次性割接自愈）；立体声配对纯靠分区名后缀 `·左`/`·右` 同前缀。**业主确认现场播放正常后明确要求"不要再改了"。**

### 20. 切换页面卡顿不丝滑（2026-07-27）
- **症状**：局域网生产环境下切页有卡顿感；同时后端持续收到并不在前台的页面的轮询请求。
- **根因**：`MainLayout` 用 `<keep-alive :max="10">` 缓存功能页，切页只触发 `onDeactivated`——**`onUnmounted` 永远不来**；而各页轮询定时器全都只在 `onUnmounted/onBeforeUnmount` 清理。逛过一圈后：电源页 5s、投影页 8s、音响页 8s 矩阵轮询（一条设备命令 ~284ms）+1s 进度秒针、空调页递归轮询、状态页 10s、首页 30s——全部在后台永续运行，每轮 fetch + 缓存页响应式重渲染把主线程周期性打断，切页动画正好撞上就是卡顿；顺带持续骚扰脆弱的单客户端设备网关。
- **根治**：新增 `composables/useActivePolling.ts`（onMounted/onActivated 启动、onDeactivated/onBeforeUnmount 停止，start/stop 幂等），六个页面全部接入；回页立即补一轮读数不等下一轮。实测：逛完全部页面后在首页静置 35s，后台 API 调用从 20+ 次降到 ~3 次（仅全局状态订阅）。
- **防回退**：新页面加轮询一律走 `useActivePolling`，禁止裸 `setInterval + onUnmounted`。

### 21. 灯光/音响页内容顶部被切 8px（2026-07-27）
- **症状**：固定壳页面（灯光/音响）KPI 条或滚动上来的卡片顶部被"切掉一部分"。
- **根因**：design-tokens.css 的全局 sticky 页头补丁（负 margin + 等量 padding + 不透明底，为"整页滚动"页面设计）与 07-26 的固定壳布局（`.v2-page overflow:hidden` + 内容区独立滚动）叠加：sticky 以 overflow:hidden 的 `.v2-page` 为滚动参照，把头部**渲染位置**推下 24px 而排版占位不变，不透明背景（z-index 60）压住内容区顶部 8px。
- **根治**：固定壳页面在 scoped 样式里整体中和全局补丁（`position:static` + 清零 margin/padding/背景/阴影）。新页面二选一：要么整页滚动享受全局 sticky 头，要么固定壳 + 中和补丁，**不能混用**。

- **components.d.ts**：自动生成且历史上被 track，拉代码常冲突——update.ps1 会先 checkout 它，**别手改**。
- **CI 不跑 seed**：新增种子数据要手工跑；`seedHardware` 遇已存在记录直接 skip，改生产数据走后台 UI。
- **设备大面积 offline 先想电源**：展厅设备（矩阵/LED/DALI/空调）没上电时 Modbus/TCP 全部超时是**正常现象**，不是服务器故障。探针输出里这些是信息性 WARN。
- **远程排障入口**：每次 CI 部署的 Actions 日志里带完整探针体检（进程分类、守护抽样、管道清单、boot-pm2.log 尾、计划任务触发器、磁盘）——先看最近一次 Actions 日志，再考虑上机。
