## 1. 架构总览

```
手机 / 平板浏览器 ── erp.cnjinhu.com/led-program ── SmartCtrl 前端（Vue3 + DS）
   │  ① 编辑节目（文字/模板/颜色/亮度）→ canvas 实时预览
   │  ② 浏览器端生成 bin（复用生成器逻辑：Uint8Array 组装）
   │  ③ POST /led-program/bin（带 admin token + 权限校验）
   ▼
SmartCtrl 后端（NestJS）— 新增 led-program 模块
   │  ④ 校验权限（RBAC：led-program:generate）→ 落播出记录/审计
   │  ⑤ 经内网通道转发 bin 到 PVE
   ▼
PVE 192.168.77.10 — 新增 bin 接收程序（bin-receiver.service）
   │  ⑥ 收到 bin → 校验 → 存盘 programs/
   │  ⑦ 调用 push_factory.py → vmbr1 组播推流
   ▼
LED 灯珠接收卡 224.1.1.1:65535 —— 大屏播出
```

**关键设计决策**
- **bin 生成在浏览器端**：与现有生成器一致，零后端算力；后端只做鉴权/审计/中转。
- **SmartCtrl 后端中转**：手机在公网（erp.cnjinhu.com），PVE 在内网（192.168.77.10），浏览器无法直连 PVE；由 SmartCtrl 后端（生产 GK9000）转发。**前提：GK9000 ↔ PVE 网络可达**（见 §5 待确认）。
- **PVE 职责**：仅作播放终端——收 bin 即推流，不存节目库、不做管理 UI。

## 2. 前端页面设计（LedProgramPage.vue）

**入口**：平板布局新增路由 `/led-program`（与 `/led` 诺瓦大屏并列，独立入口避免推错屏）。

**页面结构**（见效果图 `LED节目制作页-效果图.html`）：
- 左栏 **实时预览**：LED 屏画布（文字即时上屏 + 动画模板实时渲染）、屏参条（22 段×1468B / ≈549pps / 224.1.1.1:65535 / vmbr1 / 亮度）、PVE 在线状态、最近生成/播出时间
- 右栏 **节目编辑**：节目文字（textarea，输入即时上屏）、动画模板（6 款：极光/流光/星点/粒子/科技网格/纯净）、文字颜色（DS 色板）、字体、背景动画开关、亮度滑条、屏幕参数折叠（默认已配置）
- 底部 **操作条**：生成 bin（primary 渐变按钮）、推流播出（danger 高权限按钮）、最近播出记录
- **RBAC 联动**：右上角角色切换（管理员/操作员/访客）真实生效——按钮禁用/可点随角色变化（效果图已实现该交互）

**样式约束（不自造轮子）**：全部走 DS tokens——`--v2-*` 色板、hairline 卡片、Element Plus 控件（el-button/el-input/el-slider/el-switch/el-select 现成组件）、lucide 图标、暗/亮双主题；复用现有 `useAdminUnlock`/`usePermissionStore` 模式。

**代码复用**：生成器 HTML 的 canvas 渲染 + bin 组装逻辑提取为 `composables/bin-generator.ts` + `assets/led-templates.ts`（模板参数数据），页面组件只管编排。

## 3. 后端设计（NestJS · led-program 模块）

```
backend/src/modules/led-program/
├── led-program.controller.ts   # POST /led-program/bin；GET /led-program/history
├── led-program.service.ts      # 鉴权 → 转发 PVE → 落记录
├── led-program.entity.ts       # led_program_play_log（播出记录）
└── pve-client.ts               # 内网 HTTP 客户端（转发 bin 到 PVE 8091）
```

**接口**
| 接口 | 方法 | 说明 | 权限 |
|---|---|---|---|
| `/led-program/bin` | POST | 接收前端生成的 bin（multipart/raw）+ 节目元数据 → 转发 PVE | `led-program:generate` |
| `/led-program/push` | POST | 触发 PVE 推流（bin 已在 PVE） | `led-program:push` |
| `/led-program/history` | GET | 最近播出记录（管理员全部/操作员本人） | `led-program:view` |
| `/led-program/status` | GET | PVE 在线/当前节目状态 | `led-program:view` |

**鉴权**：复用现有 admin-auth（JWT + role）；权限点校验层读取 RBAC（生产库 rbac 表；本地旧库无 rbac 表时按角色兜底：admin=全量、operator=generate/view、viewer=view）。

**审计**：push 动作写 `audit_logs`（现有表）+ `led_program_play_log` 新增表。

## 4. PVE 接收程序（bin-receiver）

```
/opt/bin-generator/
├── bin_receiver.py        # 新增：HTTP POST 接收 → 校验 → 存盘 → 触发推流
├── push_factory.py        # 已有：帧组装 + 组播推流 224.1.1.1:65535（22段×1536B，payload[0:1468]）
├── programs/              # 新增：接收的 bin 存盘目录（最近 N 个，可滚动清理）
└── bin-receiver.service   # 新增 systemd：监听 8091（8090 保持文件服务不动）
```

**bin_receiver.py 流程**
1. `POST /bin/receive`：接收 bin 文件（校验魔数/长度=22×1536=33792B）→ 存 `programs/<name>.bin`
2. 写状态文件 `programs/current.json`（节目名/时间/校验值）
3. 调用 `push_factory.py <programs/<name>.bin`（复用现有帧格式实现）→ vmbr1 组播推流
4. 返回 `{ok, pushed: true}`；失败返回结构化错误（SmartCtrl 后端透传前端 toast）

**网络前置**：推流前 `bridge link set dev vmbr1 snooping off`（已有结论）；218.x 红线不动；vmbr1 只用 192.168.1.250/24。

## 5. RBAC 权限设计

**权限点**（生产 `rbac_permission` 表新增 3 条，原子化设计对齐现有 54 权限点体系）

| 权限点 code | 含义 | 说明 |
|---|---|---|
| `led-program:view` | 查看节目页/试播预览 | 读操作，全角色 |
| `led-program:generate` | 生成 bin 文件 | 制作节目，不改变现场 |
| `led-program:push` | 推流播出 | **高风险**——立即改变现场大屏内容，需确认弹窗 |

**角色矩阵**

| 角色 | view | generate | push | 说明 |
|---|---|---|---|---|
| 管理员 (admin) | ✓ | ✓ | ✓ | 默认全量 |
| 操作员 (operator) | ✓ | ✓ | — | 可制作不可播出；如现场需要，管理员在 RBAC 后台单独授权 |
| 访客 (viewer) | ✓ | — | — | 只读，可试播预览（本地预览不推流） |

**落库与兜底**
- 生产：3 权限点写入 `rbac_permission`，默认角色绑定（admin 全绑、operator 绑 view+generate）——走生产库 migration（`migrations/7x-led-program.sql`，生产已到 migration 70，本地旧库 25——**迁移仅生产执行，本地库不升级 schema**）
- 本地开发：`usePermissionStore` 扩展 `canLedPush = role==='admin'` / `canLedGen = role!=='viewer'`，与现有前端权限模式一致；后端按角色兜底校验
- 审计追溯：push 落 `audit_logs`（operator_id/ip/时间/节目名/bin 摘要），历史页按角色过滤

**界面体现**（效果图已实现）：按钮随角色禁用 + hover 提示权限要求；推流前二次确认弹窗（节目名 + 目标地址 + 警告）。

## 6. 植入步骤（分阶段，每阶段本地验收后经业主确认再进下一步）

## 7. 风险与待确认

| # | 项 | 影响 | 需要业主拍板 |
|---|---|---|---|
| 1 | **GK9000 ↔ PVE 网络可达性** | 中转方案成立的前提；不可达则需反向 SSH 隧道/VPN 或 PVE 暴露受限端口 | 现场确认或授权隧道方案 |
| 2 | 页面入口 | 建议平板端 `/led-program`（手机可操作）；如要进后台管理端则改 `/admin/led-program` | 二选一 |
| 3 | operator 推流权限 | 默认禁（需管理员授权）；如现场常态运营希望操作员可播，改默认授权 | 授权策略 |
| 4 | bin 生成端 | 浏览器端（推荐，零后端算力）；如担心手机性能可改后端生成（PVE 8090 已有 python 环境） | 性能取舍 |
| 5 | 8090 vs 8091 | 接收程序独立端口 8091，避免动现有服务 | — |
| 6 | 本地库不升级 schema | RBAC 表仅生产有；本地前端 store 兜底 | 已按此设计 |
