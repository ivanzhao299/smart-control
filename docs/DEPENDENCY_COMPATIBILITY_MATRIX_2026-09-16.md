# 生产依赖兼容与安全升级矩阵（2026-09-16）

## 1. 治理原则

1. 后端与前端分别升级、分别验证、分别部署，避免把两个运行时的兼容风险叠加。
2. 先删除未使用的依赖，再升级直接依赖，最后才使用精确版本覆盖解决上游尚未发布补丁的问题。
3. 每批必须通过锁文件冻结安装、生产依赖审计、全量测试、构建、空库迁移演练和生产部署验证。
4. CI 和生产发布在发现 `critical` 或 `high` 公告时失败；`moderate` 只能在记录调用路径、责任批次和处理期限后暂时保留。
5. 锁文件是安装版本的唯一依据。包清单只声明兼容范围，CI 与生产统一使用 pnpm 10.33.4 和 `--frozen-lockfile`。

## 6. 供应链批次 P0-C4

- 前后端每次锁文件变更及每周定时生成独立 SPDX JSON SBOM，产物绑定提交号并保留 90 天。
- SBOM 从只安装生产依赖的目录生成；安装时禁用依赖脚本，并校验包数量、版本信息和关键生产包。
- Dependabot 每周为后端、前端和 GitHub Actions 创建受控 PR，不自动合并；应用依赖主版本继续按独立兼容批次处理。
- 所有工作流统一到 pnpm 10.33.4 和当前官方 action 主版本；第三方 SBOM action 固定到不可变提交。
- 纯文档和 GitHub 工作流变更不再触发现场生产部署，减少无运行时变化的服务重启；生产部署脚本、应用代码、依赖和配置变更仍正常部署。

本地使用与 CI 相同的 Syft 1.51.1 从干净的生产依赖目录生成清单：后端 310 个包、619 条关系，前端 82 个包、163 条关系；开发工具 Jest/Vite 未进入对应生产清单，关键生产包与版本信息校验通过。后端生产审计、60 套件/643 项测试和构建通过；前端生产审计、52 项测试、类型检查和 PWA 构建通过。远端产物证据在 PR 任务完成后补充。
